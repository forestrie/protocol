# Conformance vectors

Three sets of public bytes. An implementation that produces or verifies
Forestrie grants, leaves, checkpoints or receipts is expected to pass all of
them; the bytes here, not any implementation, are the reference.

| Set | Files | What it fixes |
|---|---|---|
| Cross-language fixtures | `fixtures/leaf_vectors.json`, `fixtures/grant_vectors.json`, `fixtures/grant_vectors_negative.json` | the leaf commitment and the grant wire format |
| Golden grant receipt | `golden/grant-genesis.cbor`, `golden/grant-receipt.cbor`, `golden/manifest.json` | a complete offline verification from a forest genesis document to a sealed grant |
| Burial bundle | `golden/burial/sth-000{0,1,2,3}.cbor`, `golden/burial/burial-receipt.cbor`, `golden/burial/manifest.json` | a retained checkpoint chain and a receipt whose peak the log has since buried |

`SHA256SUMS` pins every data file under `vectors/`; `sha256sum -c
vectors/SHA256SUMS` from the repository root checks them, and CI checks that
the pin list is complete. Markdown under `vectors/` is not pinned, so a change
to `SHA256SUMS` always means changed vector bytes.

## Provenance

The fixture files were generated by the Go implementation's vector generator
and the golden sets by the TypeScript verifier's exporters, then frozen here.
This repository is now their source of truth: implementations copy from it,
and a divergence is a bug in the implementation.

The golden sets **cannot be regenerated**: both exporters mint a random
signing key per run, so re-running them produces different, equally valid
bytes rather than these. Carry the committed bytes forward.

The `comment` field in each golden manifest is part of the frozen bytes and
is left as the exporter wrote it; the ticket references it carries are
historical and are exempted from this repository's link checks.

## Cross-language fixtures

The grant and leaf formats are specified in
[log authority and grants](../spec/log-authority-and-grants.md) (§2.1 for the
wire map, §4 for the commitment). [grant-and-leaf-format.md](grant-and-leaf-format.md)
walks through them with code in three languages.

**`leaf_vectors.json`.** Each entry gives the grant fields and the two
digests every implementation must reproduce: `expected_inner_hex`, the
SHA-256 of the inner preimage (the value a sequencer commits as the content
hash), and `expected_leaf_hex`, the leaf commitment
`SHA-256(idtimestamp ‖ inner hash)`.

**`grant_vectors.json`.** Each entry gives the same fields plus
`expected_cbor_hex`, the response-form grant map (keys `0`–`6`, key `0` the
idtimestamp) in Core Deterministic Encoding. Decoding the bytes must yield
the fields, and re-encoding the fields must yield the bytes exactly. The
payload form omits key `0` and is otherwise identical.

**`grant_vectors_negative.json`.** Each entry is a map a conforming decoder
must reject, with `must_reject: true`, a `reason`, and the offending keys.
The current entries carry the retired keys `7` (signer) and `8` (kind). A
decoder passes by refusing them; the shape of the error is the
implementation's own.

`scripts/check-vectors.py` recomputes both positive files from their fields
with the Python standard library and checks that each negative entry really
contains a key outside `0`–`6`.

## Golden grant receipt

A forest genesis document, and the receipt for a grant sealed in the root
authority log of that forest.

| Input | Where it comes from |
|---|---|
| `genesisCbor` | `grant-genesis.cbor` |
| `receiptCbor` | `grant-receipt.cbor` |
| the grant | `manifest.json`: `logId`, `ownerLogId`, `grantFlagsHex`, `maxHeight`, `minGrowth`, `grantDataHex` |
| the idtimestamp | `manifest.json`: `idtimestampBe8Hex` |

Entry point in the published verifier: `verifyGrantReceiptOffline` in
`@forestrie/receipt-verify`. The trust root is the genesis document's
bootstrap key (a signature root); nothing is read from a chain or an
operator.

| Case | Expected result |
|---|---|
| as committed | `{ ok: true, stage: "binding" }` |
| any receipt byte flipped | `signature_invalid` |
| any genesis byte flipped | `genesis_invalid` |
| the idtimestamp changed | `signature_invalid` |

The grant's `ownerLogId` equals its `logId` because the vector is a root
authority log's own grant, and the flags `0000000300000001` mark it an
auth-log grant with create and extend authority. Both values enter the leaf
commitment; with any other values the receipt fails `signature_invalid`.

## Burial bundle

Four consecutive checkpoints of one log and a receipt issued while the log
had three entries. The chain folds `0 → 3 → 7 → 10 → 15`: each checkpoint
carries a consistency proof from the previous sealed size, and each is signed
over the accumulator it produces. The final accumulator is one peak,
`finalAccumulatorHex[0]`.

The receipt's peak, `buriedPeakHex`, is **absent** from the final accumulator
(the log grew past it) and **present** in the accumulator of link 0. The
receipt is therefore still verifiable: its inclusion path recomputes the
buried peak from `leafHashHex` at `leafMmrIndex`, its signature verifies over
that peak, and the chain proves the peak was sealed.

Entry points in the published verifier: `verifyCheckpointChain`,
`parseReceipt` and `calculateRoot`. The trust root is the sealer's public
key, `publicKeyXyHex` (a known-key signature root).

| Case | Expected result |
|---|---|
| the chain as committed | `ok`, four links, accumulator equal to `finalAccumulatorHex` |
| any byte of checkpoint *i* flipped | the fold fails at link *i* |
| any receipt byte flipped | the signature over the recomputed peak fails |
| a different leaf hash | the path does not reach the buried peak |

## Running the checks

```
python3 scripts/check-vectors.py
python3 scripts/check-pins.py
sha256sum -c vectors/SHA256SUMS
npm ci --prefix scripts/verify-golden && node scripts/verify-golden/verify.mjs
```

The last command uses the published verifier packages at the versions pinned
in `scripts/verify-golden/package.json`. Every case in the tables above is
asserted there.
