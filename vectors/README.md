# Conformance vectors

Nine sets of public bytes. An implementation that produces or verifies
Forestrie grants, leaves, checkpoints, receipts, delegate-key vouchers,
KS256 signatures, delegated-spend statements, payment nonces or delegated
payments is
expected to pass the sets for what it handles; the bytes here, not any
implementation, are the reference.

| Set | Files | What it fixes |
|---|---|---|
| Cross-language fixtures | `fixtures/leaf_vectors.json`, `fixtures/grant_vectors.json`, `fixtures/grant_vectors_negative.json` | the leaf commitment and the grant wire format |
| Checkpoint receipt KAT-39 | `fixtures/checkpoint-receipt-kat39.json`, described in [checkpoint-receipt-format.md](checkpoint-receipt-format.md) | the consistency fold, the rejected proof shapes, the protected-header conformance classes, and signed receipts of consistency under both algorithms |
| Golden grant receipt | `golden/grant-genesis.cbor`, `golden/grant-receipt.cbor`, `golden/manifest.json` | a complete offline verification from a forest genesis document to a sealed grant |
| Burial bundle | `golden/burial/sth-000{0,1,2,3}.cbor`, `golden/burial/burial-receipt.cbor`, `golden/burial/manifest.json` | a retained checkpoint chain and a receipt whose peak the log has since buried |
| Delegate-key voucher | `fixtures/delegate-key-voucher.json` | the registrar voucher's claims map, including claim 4 (`notAfter`), and its expiry rule |
| KS256 low-s | `fixtures/ks256-low-s.json` | the `s` bound applied by every verifier that recovers a KS256 signer |
| Payment nonce | `fixtures/payment-nonce.json` | the nonce that ties a payment to the grant, onboarding or credit purchase it pays for, and the preimages no request derives |
| Delegated-payment binding | `fixtures/erc7710-leaf-salt-v1.json` | which delegation in a receipt binds a payment, the `Transfer` it pairs with, and the request it pays |
| Delegated-spend statements | `fixtures/erc7710-statements.json` | the ERC-7710 delegation hash a statement carries, the delegation statement's bytes, the leaf the on-chain publication check rebuilds, and the auditor's verdict on every tagged hash |

`SHA256SUMS` pins every data file under `vectors/`; `sha256sum -c
vectors/SHA256SUMS` from the repository root checks them, and CI checks that
the pin list is complete. Markdown under `vectors/` (this file,
`grant-and-leaf-format.md`, `checkpoint-receipt-format.md`) is not pinned, so
a change to `SHA256SUMS` always means changed vector bytes.

## Provenance

The grant and leaf fixtures were generated by the Go implementation's vector
generator, the KAT-39 file by the Python reference implementation, the
golden sets by the TypeScript verifier's exporters, the voucher by the
custodian's builder in arbor, the KS256 low-s set by Foundry's `cast`
(see [KS256 low-s](#ks256-low-s)), and the delegated-spend sets by
`scripts/gen-delegated-spend-vectors.py`; all were then frozen here. This repository is now their source of truth: implementations copy
from it, and a divergence is a bug in the implementation.

The golden sets **cannot be reproduced**: both exporters mint a random
signing key per run, so re-running them produces different, equally valid
bytes rather than these. They were regenerated once, when the checkpoint
format gained the signed `tree-size-2` ([checkpoints-and-receipts.md](../spec/checkpoints-and-receipts.md)
§1.3), and the bytes here are that regeneration: the burial checkpoints
carry `-65933` in their protected header and low-s signatures. Carry the
committed bytes forward.

The `comment` field in each golden manifest is part of the frozen bytes and
is left as the exporter wrote it; the ticket references it carries are
historical and are exempted from this repository's link checks.

## Cross-language fixtures

The grant and leaf formats are specified in
[log authority and grants](../spec/log-authority-and-grants.md) (§2.1 for the
wire map, §4 for the commitment). [grant-and-leaf-format.md](grant-and-leaf-format.md)
walks through them with code in three languages.

**`leaf_vectors.json`.** Each entry gives the grant fields and the two
digests every implementation must reproduce: `expected_inner_hex`, the
SHA-256 of the inner preimage (the value a sequencer commits as the content
hash), and `expected_leaf_hex`, the leaf commitment
`SHA-256(idtimestamp ‖ inner hash)`.

**`grant_vectors.json`.** Each entry gives the same fields plus
`expected_cbor_hex`, the response-form grant map (keys `0`–`6`, key `0` the
idtimestamp) in Core Deterministic Encoding. Decoding the bytes must yield
the fields, and re-encoding the fields must yield the bytes exactly. The
payload form omits key `0` and is otherwise identical.

**`grant_vectors_negative.json`.** Each entry is a map a conforming decoder
must reject, with `must_reject: true`, a `reason`, and the offending keys.
The current entries carry the retired keys `7` (signer) and `8` (kind). A
decoder passes by refusing them; the shape of the error is the
implementation's own.

`scripts/check-vectors.py` recomputes both positive files from their fields
with the Python standard library and checks that each negative entry really
contains a key outside `0`–`6`.

## Golden grant receipt

A forest genesis document, and the receipt for a grant sealed in the root
authority log of that forest.

| Input | Where it comes from |
|---|---|
| `genesisCbor` | `grant-genesis.cbor` |
| `receiptCbor` | `grant-receipt.cbor` |
| the grant | `manifest.json`: `logId`, `ownerLogId`, `grantFlagsHex`, `maxHeight`, `minGrowth`, `grantDataHex` |
| the idtimestamp | `manifest.json`: `idtimestampBe8Hex` |

Entry point in the published verifier: `verifyGrantReceiptOffline` in
`@forestrie/receipt-verify`. The trust root is the genesis document's
bootstrap key (a signature root); nothing is read from a chain or an
operator.

| Case | Expected result |
|---|---|
| as committed | `{ ok: true, stage: "binding" }` |
| any receipt byte flipped | `signature_invalid` |
| any genesis byte flipped | `genesis_invalid` |
| the idtimestamp changed | `signature_invalid` |

The grant's `ownerLogId` equals its `logId` because the vector is a root
authority log's own grant, and the flags `0000000300000001` mark it an
auth-log grant with create and extend authority. Both values enter the leaf
commitment; with any other values the receipt fails `signature_invalid`.

## Burial bundle

Four consecutive checkpoints of one log and a receipt issued while the log
had three entries. The chain folds `0 → 3 → 7 → 10 → 15`: each checkpoint
carries a consistency proof from the previous sealed size, signs the size it
proves to under protected label `-65933`, and is signed over the accumulator
it produces. The final accumulator is one peak, `finalAccumulatorHex[0]`.

The receipt's peak, `buriedPeakHex`, is **absent** from the final accumulator
(the log grew past it) and **present** in the accumulator of link 0. The
receipt is therefore still verifiable: its inclusion path recomputes the
buried peak from `leafHashHex` at `leafMmrIndex`, its signature verifies over
that peak, and the chain proves the peak was sealed.

Entry points in the published verifier: `verifyCheckpointChain`,
`parseReceipt` and `calculateRoot`. The trust root is the sealer's public
key, `publicKeyXyHex` (a known-key signature root).

| Case | Expected result |
|---|---|
| the chain as committed | `ok`, four links, accumulator equal to `finalAccumulatorHex`; every link's signed size equals its declared size |
| any byte of checkpoint *i* flipped | the fold fails at link *i* |
| links 2 and 3 alone, from the size-7 state as trusted base | `ok` |
| links 2 and 3 alone, from the size-3 state as trusted base | `size_mismatch` |
| any receipt byte flipped | the signature over the recomputed peak fails |
| a different leaf hash | the path does not reach the buried peak |

## Delegate-key voucher

The custodian's registrar voucher attests that a standing delegate public key
was derived for a sealer and epoch. It is an untagged COSE_Sign1 (ES256,
content type `application/forestrie.delegate-key-voucher+cbor`) whose payload
is the Core Deterministic map `{1: sealerId (tstr), 2: epoch (uint), 3:
delegate public key as canonical COSE_Key (bstr), 4: notAfter (uint, Unix
seconds)}`. Claim 4 bounds how long a voucher can be replayed to register its
key; vouchers issued before it was added carry claims 1 to 3 only.

`delegate-key-voucher.json` gives the registrar key (`public_key_xy_hex`, the
64-byte `x‖y` form a coordinator pins, and the test scalar
`private_key_d_hex`, never a deployed key) and three vouchers for the same
key, each with its claims, `payload_hex` (the claims re-encoded),
`voucher_hex` and cases of `now`. `not_after` is omitted from `claims` when
the voucher has no claim 4.

| Voucher | Case | Expected result |
|---|---|---|
| every voucher | claims re-encoded | byte-identical to `payload_hex`, and to the voucher's payload |
| every voucher | signature against the registrar key | verifies |
| claim 4 set | `now` before `not_after` | `ok` |
| claim 4 set | `now` equal to or after `not_after`, whether or not claim 4 is required | `expired` |
| claim 4 absent | claim 4 not required | `ok` |
| claim 4 absent | claim 4 required | `not_after_missing` |
| claim 4 is `0` | either | `expired`: the claim is present, not absent |

Claims decode strictly: a duplicated key or a claim outside 1 to 4 is
refused. The vouchers cannot be reproduced: ES256 signatures
are randomised, so rerunning the generator gives different, equally valid
bytes. Copies live in canopy `packages/shared/encoding/src/testdata/` and
arbor `services/custodian/src/testdata/`, each pinned by this file's SHA-256.

## KS256 low-s

A KS256 signature is checked by recovering its signer, and recovery alone
accepts both `s` and `n − s`: from any signature, anyone can make a second
one that recovers the same address. [checkpoints-and-receipts.md](../spec/checkpoints-and-receipts.md)
therefore requires a recovered KS256 signature to be low-s, `s ≤ n/2` with
`n` the secp256k1 group order, as it requires of ES256. `n` is odd, so the
largest `s` accepted is `(n − 1)/2`, the bound the cases below use.

`ks256-low-s.json` is one protected header (`{1: -65799}`) and payload,
and four signatures over their `Sig_structure`. The payload is the
canonical CBOR map `{1: h'…'}`, because a verifier that decodes the payload
before the signature (arbor's delegation certificate check requires a
canonical integer-keyed map) must still reach the `s` check. Each case gives the
signature as 65 bytes `r ‖ s ‖ v`, with `v` the recovery id 0 or 1, the
untagged COSE_Sign1 that carries it, and the address it recovers to.
`digest_hex` is `keccak256(Sig_structure)`, for verifiers that take the
digest rather than the message.

| Case | `s` | Expected result |
|---|---|---|
| `accept/low-s` | the test key's RFC 6979 signature, below the bound | accept |
| `reject/high-s` | `n − s` of `accept/low-s`, with `v` flipped | reject, `signature_malleable` |
| `accept/s-at-bound` | `(n − 1)/2`, the largest accepted | accept |
| `reject/s-above-bound` | `(n + 1)/2`, the smallest rejected | reject, `signature_malleable` |

Each reject case recovers the same address as its accept twin, so only the
`s` check rejects it. The accept cases keep the reject cases honest: a test
that rejects `reject/high-s` but not `accept/low-s` has shown only that the
verifier refuses the input. The second pair fixes the comparison at the
bound. Its signer is the address that signature recovers to, and no one
holds its key. The ERC-1271 path, where a contract signer judges its own
signature, is outside this vector.

The bytes can be reproduced: `accept/low-s` is the deterministic RFC 6979
signature by the test scalar in `test_key`, and each other case is derived
from it as its `note` says. To re-sign it, run `cast wallet sign --no-hash
--private-key 0x<private_key_d_hex> 0x<digest_hex>` (Foundry); `cast`
prints `v` as 27 or 28, and the vector stores the recovery id, `v − 27`.
`scripts/check-vectors.py` recomputes the
`Sig_structure` and digest, recovers every signature with the standard
library, and checks each verdict against the bound and each reject case
against its twin.

## Delegated-spend statements

The statement types are specified in
[delegated-spend-statements.md](../spec/delegated-spend-statements.md).
`erc7710-statements.json` holds test keys and accounts, ERC-7710
delegations, signed statements and audit cases. Every key is
`keccak256(label) mod n` and every signature is deterministic (RFC 6979), so
`python3 scripts/gen-delegated-spend-vectors.py` reproduces the file byte
for byte, and `--check` says whether it would change.

**`delegations`.** Each delegation gives the framework fields and the three
values a verifier must reproduce: `struct_hash_hex`, the delegation hash a
statement carries; `domain_separator_hex`; and `typed_data_digest_hex`, the
value the delegator signs. `D_AB` is signed by an EOA, so its signature
recovers to its delegator. `D_HA` is signed for a smart account, which checks
its owner's signature, so it recovers to the owner. `leaf/credits` and
`leaf/seller` are payment leaves beneath `D_AB`, never published: each pins
one USDC transfer and allows one call, and `leaf/credits` carries the
credits payment nonce as its salt.

**`statements`.** Each statement gives its fields, its bytes
(`cose_sign1_hex`, a KS256 COSE_Sign1, untagged except in the `-tag18` vector,
which carries a leading `0xd2`) and, for a delegation
statement, `publication`: the bytes before and after `DELEGATION_TAG ‖ H`,
an idtimestamp and the leaf `SHA-256(idtimestamp ‖ SHA-256(statement))`,
which is what the on-chain publication check rebuilds.

| Case | Expected result |
|---|---|
| the fields of every statement | re-encode to its payload byte for byte |
| every statement signature | recovers, low-s, to the statement's `kid`, which is never a delegation signer |
| a delegation statement | key 2 is `DELEGATION_TAG ‖` the struct hash of key 5, and `prefix ‖ TAG ‖ H ‖ suffix` is the statement |
| a revocation or spend statement | key 8 is the bare hash, and the bytes never hold `DELEGATION_TAG` |
| `spend/credits` | the payment nonce over its purpose and `D_HA`'s delegator is the salt of the leaf at key 8 |

**`audit_cases`.** Each gives statement bytes and every publication an
auditor finds in them: the offset of `DELEGATION_TAG`, the hash `H` after
it, the verdict and the signer the statement's signature recovers to. Each
also gives `route`: whether a registration service accepts the statement
or refuses it because a revocation or spend statement holds the tag.

| Case | Publication | Verdict |
|---|---|---|
| `well-formed/D_AB` | `H(D_AB)` | `well-formed` |
| `flag/hash-mismatch` | `H(D_HA)`, while key 5 shows `D_AB` | `flag:hash-mismatch` |
| `flag/signed-digest-not-struct-hash` | the digest `D_AB`'s delegator signed | `flag:hash-mismatch` |
| `flag/tag-in-another-statement-type` | `H(D_AB)`, in a statement of another content type | `flag:outside-key-2` |
| `refuse/spend-with-tag` | `H(D_AB)`, in a spend statement's unprotected header | `flag:outside-key-2`, and the route refuses it |
| `well-formed/D_AB-tag18` | `H(D_AB)`, in a tag-18 delegation statement | `well-formed`, one byte later than in `well-formed/D_AB` |
| `refuse/spend-with-tag-tag18` | `H(D_AB)`, in a tag-18 spend statement's unprotected header | `flag:outside-key-2`, and the route refuses it |

**`map_key_order` is provisional.** It is a map whose labels differ in
encoded length (`1`, `100`, `-1`), with its bytes in bytewise order and in
length-first order. Which order is canon for such labels is not settled
(see [implementation-status.md](../spec/implementation-status.md)), so the
entry carries `status: provisional` and `canonical: unsettled`, and the
check fails if either changes before the order is decided. No statement in
the file has such labels, so no other vector depends on the order.

`scripts/check-vectors.py` recomputes every hash, digest, signer and leaf,
decodes every statement strictly, and runs the audit on each case's bytes.
`--self-test` mutates the delegated-spend fixtures in memory and fails
unless the checks catch every mutation.

## Payment nonce

The nonce is specified in
[payment-nonce-and-binding.md](../spec/payment-nonce-and-binding.md) §2.
Each entry of `vectors` in `payment-nonce.json` gives a purpose's kind and
fields, the payer, and the three values every implementation must
reproduce: `purpose_digest_hex`, `preimage_hex` (79 bytes) and
`nonce_hex`. A credits entry also gives `purchase_id_hex`, the SHA-256 of
its `Idempotency-Key`. The grant purpose is the payload form, keys `1` to `6`,
of the golden grant in `grant_vectors.json`, and the check requires that.

| Case | Expected result |
|---|---|
| each kind | digest, preimage and nonce recompute from the fields |
| the same grant under two payers, and the same count under two keys | four distinct nonces |
| each `not_canonical` entry | its preimage is not canonical, and `salt_hex` is its SHA-256: no request can bind a payment with that salt |

## Delegated-payment binding

The rule is `erc7710-leaf-salt/v1`, in
[payment-nonce-and-binding.md](../spec/payment-nonce-and-binding.md) §3.
`erc7710-leaf-salt-v1.json` gives the verifier's configuration (USDC, the
payee, and the listed delegation manager with its enforcers), the leaves
and hops the receipts redeem, and one receipt per case: its logs as
`eth_getTransactionReceipt` returns them, with `log_names` for readers.
Each case expects:

| Field | Meaning |
|---|---|
| `eip3009_transfers` | positions of `Transfer` logs made under an EIP-3009 authorization |
| `chains` | each rebuilt chain, leaf first, its root and its binding delegation |
| `pairs` | each binding delegation and the position of the `Transfer` it takes |
| `unpaired_bindings` | binding delegations that found no `Transfer` |
| `payments` | identity (manager, delegation hash; the chain is the config's `chain_id`), salt, root, amount and `Transfer` |
| `unbound_transfers` | positions of `Transfer` logs to the payee that no payment holds |

`requests` names a purpose from `payment-nonce.json` and the payment it
binds, or `null`. `repay` checks that a varied leaf binds the same nonce
under another identity, and that other `args` leave a leaf's hash
unchanged. The cases are listed in the spec's §3.4.

## Running the checks

```
python3 scripts/check-vectors.py
python3 scripts/check-vectors.py --self-test
python3 scripts/gen-delegated-spend-vectors.py --check
python3 scripts/check-pins.py
sha256sum -c vectors/SHA256SUMS
npm ci --prefix scripts/verify-golden && node scripts/verify-golden/verify.mjs
```

The last command uses the published verifier packages at the versions pinned
in `scripts/verify-golden/package.json`. It decodes the grant fixtures and
asserts every case of the golden
grant receipt and the burial bundle. The delegate-key voucher and KS256 low-s
cases are checked by `scripts/check-vectors.py`, and by each implementation's
own tests against its pinned copy.
